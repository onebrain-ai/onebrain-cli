# 0023 — Warm daemon owns the search engine for MCP + CLI search

- **Status:** accepted
- **Date:** 2026-07-05

## Context

The native-search engine (ADR 0021) stores its metadata in `engine.redb`, and **redb is single-process / single-writer**: exactly one process may open a given collection's database at a time. A second opener fails with `Database already open`.

Today every search surface opens its own engine per use:

- `GET /api/vault/search` (webui) opens `Engine`/`LexIndex` **per request** (`server/search.rs`).
- The CLI `onebrain search …` verbs open an engine per invocation (`search_common::open_engine`).
- The native MCP server (`commands/mcp.rs`) opens one for its `query`/`status` tools.

As long as only one runs at a time this is fine. But the product direction is multiple concurrent sessions (agent-teams, the webui, and CLI all live at once), and the reindex-on-write hook fires from whichever session just wrote a note. Two of those opening the vector engine simultaneously hit redb's single-writer limit. We need exactly ONE long-lived engine owner, with the other surfaces talking to it.

An existing HTTP surface already runs in-process: `onebrain serve` / `daemon __run` share `crate::server` (an Axum app on `127.0.0.1` behind a per-session token). The daemon (`daemon start`/`stop`/`status` + the detached `__run` body) already exists but opened the engine per-request like everyone else and had no concurrent-start guard.

## Decision

**The warm daemon becomes the sole redb owner; MCP + CLI search become HTTP clients of it.** Transport is the **existing localhost Axum HTTP surface + the existing token auth** — no new IPC mechanism.

Concretely, Track 2a built the **daemon side + the reusable client library**; the MCP + CLI client wirings are separate tracks. **Track 2b (this update) wired the MCP server in:** `commands/mcp.rs` now obtains a daemon via `ensure_running()` and routes its `status`/`query` tools through `DaemonHandle` (`/api/internal/status` + `/api/vault/search`) instead of opening its own engine — `get`/`multi_get` stay filesystem reads, and a direct single-process engine open is kept as the daemon-unavailable fallback. **Daemon-routed `query` deltas** (on record, not overclaimed as parity): results are DOC-level (dedup/fusion keys on `path`, ≤1 hit per document, vs multiple chunks per doc directly), a `vec` sub-query is served as `hybrid` (lex mixed in) on the wire, and the daemon caps candidates at `TOP_K`=20 per sub-query (direct over-fetches ≥30); `hyde`≡`vec` on BOTH paths already, so no NEW hyde loss. `status`'s response shape is identical on both paths. The CLI `search` verb wiring remains a follow-up track.

1. **Persistent engine.** `daemon __run` opens the engine ONCE at boot and holds it in `Arc<Mutex<Engine>>` (`server::SharedEngine`) on `AppState.search_engine` for the process lifetime. `GET /api/vault/search` uses the held engine (hybrid) instead of opening per-request; lex stays on the standalone `LexIndex` (tantivy only — it never touches redb, so it can't clash). `serve` and the unit-test router leave the engine unheld (`hold_engine: false`) and keep the per-request behaviour, since a foreground `serve` is short-lived and not the canonical owner.

2. **Internal endpoints** (token-gated, same middleware as the rest of the surface):
   - `POST /api/internal/reindex` — body `{ "mode": "pending" | "paths", "paths"?: [..] }`. `pending` embeds exactly `Engine::pending_vector_paths` (mirrors `search reindex --pending-only`); `paths` runs `Engine::reindex_paths` over caller-supplied doc paths. **Every `paths` entry is confined to the vault at the HTTP layer** (`api::confine_reindex_path`) BEFORE it reaches the engine — absolute paths, `..` traversal, symlink-escapes, and tooling dirs are rejected with 400, so a caller can't steer `vault_root.join(doc_path)` + `std::fs::read` outside the vault. As defense-in-depth (#175), the **engine** confines each path too (`engine::confine_reindex_doc_path`, called from `reindex_paths`): it rejects absolute/`..`/symlink-escape as "outside the vault", so the DIRECT reindex path that never touches this HTTP layer (`ONEBRAIN_NO_DAEMON=1`, daemon-unavailable fallback, plain `onebrain search reindex <paths>`) is confined by the same rule. Writes serialise on the engine mutex.
   - `GET /api/internal/status` — the real `{ doc_count, pending_new, pending_changed, pending_removed, pending_total, last_indexed, indexed }` from the held engine (the `search status` shape).
   - `GET /api/health` — an **engine-INDEPENDENT** liveness route: 200 (`{ ok, engine_held }`) whenever the process is up, regardless of whether an engine is held. This is what the client's `is_live()` probes. The `/internal/*` routes 503 when no engine is held (internal callers depend on the single-owner invariant and never fall back to a per-request open), but liveness MUST NOT depend on the engine — see the `is_live` fix below.

3. **Discovery** — the daemon publishes `~/.onebrain/run/daemon.json` = `{ port, token, pid, version, vault }` after it binds (0600, atomic temp-then-rename) and removes it on clean shutdown. `port` is the ACTUAL bound port (matters when binding `0`); `version` is the daemon CLI's own `CARGO_PKG_VERSION`; **`vault` is the CANONICAL path of the bound vault** (`null` if bound vault-less). Because the daemon is a machine singleton, `vault` lets a client detect that a running daemon is serving a DIFFERENT vault than the caller resolved and restart it (see `vault_decision` in #5) — otherwise the caller's `query`/`status` would silently route through the wrong vault's engine. An old `daemon.json` with no `vault` key deserializes to `null` (serde default), so a pre-vault-field daemon is never trusted to be serving the right vault.

4. **Concurrent-start guard** (was missing) — `daemon start` takes an exclusive `O_EXCL`-create lock (`daemon.lock`) around the check-then-spawn window. The lock is **self-describing**: it records the creating `daemon start` PID, and a contender reclaims it ONLY if that PID is provably dead (a crashed starter) — a live creator, or an unreadable PID, is respected. Critically, the reclaim keys off the LOCK's PID, NOT the daemon PID file (which isn't written yet during a fresh concurrent start — that was the initial bug: a daemon-PID probe read "not running" and every racer reclaimed + spawned). The winner ALSO holds the lock until the daemon has published `daemon.json` (fully bound), so serialized racers always observe a running daemon and back off. Result: N simultaneous `daemon start` → exactly one daemon. `create_new` maps to `O_EXCL`/`CREATE_NEW`, so this is cross-platform — no `flock`, no nix `fs` feature. **Wedged-lock recovery:** a SIGKILL'd `daemon start` can leave `daemon.lock`, and if the OS recycles that PID onto an unrelated live process the lock never looks stale (`pid_exists` stays true) → `start` would report "already running" forever. `daemon stop` now also unlinks `daemon.lock` (both branches), so `onebrain daemon stop` is the CLI recovery. **Caveat (stop-vs-start):** because `stop` unlinks the lock unconditionally, a `stop` racing a concurrent in-flight `start` (lock held, `daemon.pid` not yet written) can let a third `start` acquire a fresh lock and spawn — so the `O_EXCL` guard *alone* no longer guarantees single-spawn under a concurrent stop. A single *serving* daemon is still guaranteed by the fixed-port bind (no `SO_REUSEADDR`/`SO_REUSEPORT` → the second bind fails `EADDRINUSE` and that child exits) plus redb's exclusive lock; the "N simultaneous starts → one daemon" result above is exact only when no `stop` overlaps. The precise fix — record the lock's start-time to tell a recycled PID from a live starter, so `stop` clears only genuinely-stale locks — is deferred to the v3.8 daemon-identity refactor.

5. **Client library** (`commands/daemon_client.rs`, reusable): `DaemonInfo` (read/write/remove of `daemon.json`); `discover()` (read + `/api/health` liveness-probe, clean up stale/dead); `ensure_running()` (spawn `daemon start` detached, poll for readiness, handle the start race by connecting to whoever won; on timeout it CLASSIFIES the last state — not-found / version-skew / alive-no-response — and names the `daemon.log` path); `DaemonHandle::search`/`reindex`/`status` (typed ureq calls carrying the token, each **retrying ONCE via `ensure_running` on a TRANSPORT error** — a vanished daemon — while an HTTP status error propagates unchanged); and version-skew handling (`version_decision` → stop + restart when `daemon.json.version != own`; a stop FAILURE is surfaced as a warning, not swallowed). **Vault-skew handling (Track 2b):** `discover`/`ensure_running` take the caller's expected vault; `vault_decision` maps a daemon bound to a DIFFERENT vault (or an old record with no vault, or bound vault-less while a vault is expected) to a RESTART, exactly like a version skew — the retry-once reconnect passes the handle's bound vault back so a respawn can't be satisfied by a wrong-vault daemon. This makes the v3.4.6 model explicit: one vault at a time per machine; switching vaults restarts the daemon (concurrent per-vault daemons deferred to v3.8).
   - **`is_live` fix (silent-failure).** `is_live()` probes `/api/health`, NOT `/api/internal/status`. Probing status would 503 for a live-but-engine-less daemon → the client would read it as dead, delete its `daemon.json`, and respawn it in a loop. The health route is engine-independent, so a running daemon is always seen as alive and its discovery record is preserved.
   - **Vault conveyed by argument, not env (v3.4.6 sweep).** The auto-start path passes the caller's vault to the spawned daemon as `daemon start --vault <path>` (threaded to the detached `daemon __run --vault …` child → `resolve_daemon_vault`), NOT by mutating the caller's `$ONEBRAIN_VAULT` via `std::env::set_var` (unsound under concurrent reads; deprecated since Rust 1.81). The MCP entrypoint (`mcp.rs`) no longer sets that env var at all. `--vault` takes precedence over `$ONEBRAIN_VAULT`, which stays a back-compat fallback for a daemon started without the arg.
   - **Uncanonicalizable expected vault → mismatch (v3.4.6 sweep).** `expected_vault` is turned into a `VaultExpectation` (`Any` / `Vault(id)` / `Unresolvable`) by `vault_expectation`, instead of `expected_vault.and_then(canonical_vault_id)` which collapsed "caller HAS a vault but it wouldn't canonicalize" into "no expectation" — and `vault_decision(_, None)` said `Use`. Now an `Unresolvable` expectation (dir vanished mid-op) is a conservative **mismatch**: the CLI routes direct and the MCP active path refuses to adopt/spawn an unverifiable daemon, closing a narrow wrong-vault TOCTOU.

6. **Lifecycle** — idle-shutdown TTL (`$ONEBRAIN_DAEMON_IDLE_SECS`, default 30 min; `0` disables), driven by an `AppState.last_activity` marker the auth middleware bumps on every authenticated request (predicate `should_idle_shutdown`); and clean SIGTERM handling that drops the engine (releasing the redb lock) and removes `daemon.json`. `daemon stop` ALSO clears ALL runtime files — `daemon.pid`, `daemon.json`, AND `daemon.lock` — in both branches, so a hard-killed daemon's stale record / a SIGKILL'd `start`'s wedged lock are cleared on the next `stop`; any remaining stale `daemon.json` is reclaimed lazily by `discover`'s liveness probe.

### High-assurance coverage (repo-owner policy)

Security/filesystem-touching daemon code is **NOT whole-file-excluded** from coverage. `daemon.rs`, `daemon_client.rs`, and `server/search.rs` were removed from the exclusion allowlist; their LOGIC (concurrent-start orchestration + lock reclaim, path confinement, `is_live`/health decision, discovery + version-skew, the retry policy, the idle-shutdown predicate) is unit-tested toward the target, plus live-server HTTP round-trips and a real-binary concurrent-start orchestration test. Only the irreducible OS/network/embed shell (fork/detach, bind, signal-wait, real embedding) remains, documented per-line under "Residual unreachable lines" in `docs/coverage.md`. The un-exclusion pulls that shell into the measured surface, so the ratchet was reset 95 → 94 (achieved ≈94.99%) as a deliberate new baseline — see `scripts/coverage.sh`.

### Rejected / deferred

- **Bespoke unix-domain socket — REJECTED (deferred to the v3.8 full daemon refactor).** A unix socket is arguably a tighter fit for a local-only IPC, but it isn't cross-platform (Windows named pipes would need a parallel path) and would mean a *second* server stack alongside the Axum one we already run for the webui. Reusing the existing HTTP surface + token auth gives cross-platform behaviour and maximum code reuse now; a socket can be revisited when the full daemon refactor consolidates all surfaces (v3.8).
- **Daemon owning ALL surfaces (config/tree/file/chat routed through it) — OUT OF SCOPE.** This PR scopes the daemon to the **search** engine ownership problem (MCP + search). The remaining surfaces still work per-request; consolidating them is the later full-refactor cleanup.
- **HTTP-layer doc-count-rise test — done download-free in a lex-only build.** A lex-only build lex-indexes a doc and records its `DOC_HASHES` hash WITHOUT embedding (`Engine::embed_passages_if_available` returns `None`), so `reindex {mode:"paths"}` over a real on-disk `.md` genuinely returns non-zero `added` and raises `doc_count` with NO model download — the HTTP end-to-end reindex-mutation test runs in the lex-only tier and checks each stat maps to the right response field. Under the `semantic` feature the same path would embed (model download), which the no-download rule forbids, so that tier asserts only the download-free arms (empty-pending no-op, confinement rejects, concurrent search+status, auth, 503). The stats→`ReindexResponse` field mapping is ALSO covered by a build-agnostic direct unit test, and engine reindex correctness by `onebrain-search`'s `FakeEmbedder` tests.

## Consequences

- With the client tracks wired in, MCP + CLI search route through the one daemon engine, so multiple concurrent sessions no longer race redb's single-writer lock.
- `serve` behaviour is unchanged (still opens per-request) — no regression for the foreground command, and every existing server test passes untouched (they build the router with `hold_engine: false`).
- The daemon now cleans up after itself: idle-shutdown releases the redb lock when unused, and `daemon.json` is removed on clean exit so a client never connects to a dead daemon.
- Version skew is handled explicitly: a client that finds a daemon at a different version restarts it before use, so a stale daemon from an older install can't serve an incompatible wire shape.
- The client library (`daemon_client.rs`) currently reads as mostly dead code (allowed at the module level) until the MCP + CLI tracks call it; its core paths are unit-tested so it isn't untested dead code.
- Windows: TCP + `O_EXCL` work everywhere, so the concurrent-start guard and discovery are cross-platform; the detached-spawn / SIGTERM parts of the daemon remain Unix-first as before (unchanged by this PR).

## Update — Track 2c: CLI search verbs wired to the daemon (v3.4.6)

The CLI-client wiring the original PR deferred has landed. The CLI `search` verbs now route through the warm daemon when one is **already running and serves the same vault**, so the CLI works while an MCP session holds the engine and auto-reindex lands in-session. It **reuses Track 2b's vault-identity mechanism** (`DaemonInfo.vault` + `vault_decision`) — no second served-vault source — and differs from the MCP path in ONE load-bearing way: it is PASSIVE.

- **Active (MCP) vs passive (CLI).** Track 2b's `discover`/`ensure_running` are the ACTIVE lifecycle owner: on a version/vault mismatch they STOP + restart the daemon for the caller's vault (§5). The CLI `search` verbs must NEVER do that — a `search` command must not kill a daemon serving another vault (a live MCP session). So the CLI adds a PASSIVE reader:
  - **`daemon_client::discover_matching(expected_vault)`** — reads `daemon.json`, and on a version OR vault mismatch (`version_decision`/`vault_decision` == `Restart`) returns `Ok(None)` **without stopping, restarting, or removing** the record. Only a live daemon (via the engine-independent `/api/health` probe) matching BOTH version and the caller's vault yields `Some(handle)`; a dead SAME-vault record is reclaimed like `discover`.
  - **`search_common::route_to_daemon(resolved)`** — `None` when `ONEBRAIN_NO_DAEMON` is set; else `discover_matching(Some(resolved.root))`. No `/api/health` `vault` field is added — the vault the client matches against comes from `daemon.json` (written at bind, its truth rung by the liveness probe).
- **New daemon endpoints/modes** (small, mirroring the existing ones): `GET /api/internal/get?path=` (the held engine's `Engine::get`; `404` → the CLI's "not indexed" hint), and reindex modes `lex` (keyword-only whole-vault, no embed — mirrors `--lex-only`, so the PostToolUse hook keeps the index current in-session without a per-write model load) and `all` (full reindex + embed — a bare `search reindex`). `ReindexResponse` also carries `embed_model` so the CLI renders the same summary as the direct path.
- **Per-verb mapping** — `query`→`GET /api/vault/search?mode=hybrid`; `status`→`/internal/status`; `get`→`/internal/get`; `reindex`→`{mode:"all"}`; `reindex <paths>`→`{mode:"paths"}`; `--lex-only`→`{mode:"lex"}`; `--pending-only`→`{mode:"pending"}`. **Not routed:** `search search` (lex uses the standalone tantivy index — no redb, no contention) and `search vsearch` (the daemon exposes no vector-only mode, so it opens directly → honest `E_ENGINE_BUSY` mid-session); `--force` reindex (it wipes the index files the daemon holds open, so it needs a daemon-free rebuild).
- **Fallback preserves T1's honest error** — when no daemon is available, it serves a different vault/version, or `ONEBRAIN_NO_DAEMON=1`, every verb opens the engine directly, so a genuinely-held lock still surfaces as `E_ENGINE_BUSY` (exit 77) / the hooks' `engine-busy` skip. The daemon path never regresses that: it only bypasses the lock because the daemon is the legitimate owner.
