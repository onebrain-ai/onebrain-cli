# 0019 — Native MCP server (`onebrain mcp`) + staged qmd cutover

- **Status:** accepted
- **Date:** 2026-07-03

## Context

The native search engine (`onebrain-search`, [ADR 0012](0012-native-search-replace-qmd.md)) needed an MCP-facing entry point so agent harnesses could query the vault the same way they already do through the external `qmd` MCP server. Two decisions had to be made together: how to host MCP over a synchronous engine, and how to cut an existing, working integration (the plugin's `qmd` MCP config + every agent instruction that names its tools) over to the new server without breaking it mid-flight.

The command started life as `search mcp` — nested under the `search` resource group alongside `query`/`reindex`/`status`. Partway through the milestone, the maintainer decided to promote it to a top-level `onebrain mcp` command instead: the MCP surface is the single entry point future tool groups (notes, tasks, other vault resources) will mount on, and burying it under `search` would misname it the moment a non-search tool group lands. This is a recorded, deliberate exception to the "minor version bump = new first-level command" convention — `mcp` is a new first-level command, but it lands in **3.4.1** (a patch) because it is a sub-deliverable of the v3.4 mini-epic ("native search replaces qmd") already in flight, not a standalone new capability announcement. The version stays 3.4.1.

## Decision

- **Architecture**: `onebrain mcp` runs an `rmcp` stdio server. tokio is confined to the MCP edge (`commands/mcp.rs`) — the engine itself (`onebrain-search::Engine`) stays synchronous, held behind `Arc<Mutex<Engine>>`, and every tool handler drives it through `tokio::task::spawn_blocking`. This keeps the engine crate free of an async runtime dependency and matches its existing single-writer-per-collection contract.
- **qmd-compatible tool surface**: the server exposes `query`, `get`, `multi_get`, `status` — the same four tools and (mostly) the same parameter names the external qmd MCP server used, so a client swap is a config change, not an instruction rewrite. Several qmd-era parameters are accepted but not yet used by the native engine: `query`'s `rerank`, `candidateLimit`, `collections`, and `intent` all deserialize successfully and are silently ignored (see field docs on `QueryParams` in `crates/onebrain-cli/src/commands/mcp.rs`) — native rerank and intent-aware ranking are relevance-phase work (v3.4.3).
- **Client-side RRF fusion**: `query` accepts 1-10 typed sub-queries (`lex`/`vec`/`hyde`); each is run independently against the engine and the ranked lists are fused client-side with Reciprocal Rank Fusion (`RRF_K = 60.0`). The first sub-query in the list gets 2x weight, every other sub-query 1x. Fused scores are then normalized so the top hit is exactly `1.0` — this preserves qmd's `minScore` semantics (a 0-1 relevance threshold) even though the underlying signal (summed RRF contributions) has no natural 0-1 range of its own.
- **Staged cutover — server key stays `qmd` in v3.4.1**: the OneBrain plugin's `.mcp.json` continues to register this server under the config key `qmd` for this release. That means the `mcp__plugin_onebrain_qmd__*` tool namespace agents already call, and every existing agent instruction that names those tools, keep working completely unchanged — only the process launched behind that key moves from the external `qmd` binary to `onebrain mcp`. The key rename (`qmd` → `search`) and the accompanying instruction rewrite across the plugin's skills is deliberately deferred to **v3.4.2**, so this milestone ships zero required changes to agent-facing instructions.
- **`session init`'s `qmd_unembedded` field is frozen as a compatibility contract.** Its JSON field name does not change even though, as of this milestone, its data now comes from a native-index probe (`Engine::status` via `native_pending`) instead of shelling out to the `qmd` binary (see the `feat(session)` / `fix(session)` commits in this branch). Consumers reading that field see no change in shape, only in how promptly and reliably it's populated (see also [ADR 0020](0020-cpu-only-embedding-runtime.md) for the time-boxing story on this probe: a 300ms cap so a large vault can't stall `SessionStart`).
- **Docs governance**: `docs/reference/mcp.md` is the canonical MCP API reference. Any PR that adds, changes, or removes an MCP tool or parameter must update that page in the same PR — enforced as a checklist line in `docs/release-checklist.md`, the same mechanism ADR 0018 used for the release-matrix gate.

## Consequences

- Agents get a fully local, dependency-free MCP search server one release before the visible tool-namespace rename — the cutover risk (breaking every agent's tool calls at once) is split into two smaller, independently-verifiable steps.
- The compat-only params (`rerank`, `candidateLimit`, `collections`, `intent`) are dead weight in the schema until v3.4.3 lands relevance work; they cost nothing at runtime (ignored) but do mean the tool's declared schema promises more than it currently does. This is documented, not hidden — `docs/reference/mcp.md` marks each as "compatibility only, not used by the native engine."
- `onebrain mcp` living at the top level (rather than under `search`) is a one-off exception to the command-tree convention; it's recorded here specifically so a future auditor doesn't read it as scope creep or an accidental deviation.
- The cache-relocation decision (issue #114, moving the model/index cache from `~/Library/Caches` to `~/Library/Application Support` on macOS) is explicitly **not** part of this ADR or this PR — it gets its own ADR when that patch lands.
