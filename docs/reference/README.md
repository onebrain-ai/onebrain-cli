# Code reference

A file/module-level map of the source, so you can land in any crate and follow the calls. For the big picture first, read [`../architecture.md`](../architecture.md); for the idioms, [`../rust-patterns.md`](../rust-patterns.md). This is the "what's in each file and how they connect" layer.

> Generated by reading the source at the documented version. Names are the stable anchor; line numbers drift. If a doc and the code disagree, the code wins — open a PR.

## Dependency direction

Higher crates depend on lower ones, never the reverse:

```
onebrain-cli ──▶ onebrain-fs ──▶ onebrain-core
       │                              ▲
       ├────────▶ onebrain-cache ─────┘
       └────────▶ onebrain-search     (standalone — no workspace deps)
```

Read order for a newcomer: **core → cache → fs → search → cli** (each builds on the one before; `onebrain-search` stands alone — read it any time before `cli`).

## How each crate doc is laid out

Every `onebrain-*.md` follows the same shape so you can skim:

1. **Purpose & dependencies** — one paragraph; what the crate owns, what it depends on, who depends on it.
2. **Module map** — the `src/` tree with a one-line role per file/module.
3. **Per-module sections** — for each module/file:
   - **Path** (`crates/<crate>/src/<file>`) and what it's responsible for.
   - **Key types** — public structs/enums/traits with a one-line purpose.
   - **Key functions** — `name(args) -> ret` with a one-line purpose.
   - **Connections** — what it calls (downstream) and who calls it (upstream / hook / command).
4. **Entry points** — where execution enters this crate (a command handler, a hook, a public `fn`).

Test modules are noted at the section level (what they cover), not enumerated function-by-function.
